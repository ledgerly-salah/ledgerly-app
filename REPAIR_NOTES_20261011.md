## Compatibility and recovery policy

- Historical `releases/20261009-integrity-r4` files remain byte-for-byte unchanged. The candidate uses a separate immutable release directory, updated manifest hashes and a distinct service-worker cache. Updates still wait for user acceptance; session module is included in the offline shell.
- Backups already exported from the device remain readable using their original passwords/keys. They cannot be remotely invalidated. After rotation, their old DEK does not decrypt future/current ciphertext.
- Changing password now creates a new recovery key if recovery is enabled. The dialog explains this before changing; the key is displayed after a successful atomic save. Export a fresh backup after changing security.
- Local snapshots are retained and re-encrypted. An unreadable snapshot aborts key rotation rather than deleting it. Legacy snapshots without a file bundle can only migrate when the required files remain available; otherwise restore the full original backup.
- The first evidence upgrade creates a rollback snapshot, authenticates all readable files, then atomically saves state and upgraded files. Failure leaves the previous bundle intact. This binds legacy metadata as observed during migration; it cannot establish the historical authenticity of metadata that was already altered before upgrade.
- File names and metadata are authenticated, not concealed; they remain visible outside ciphertext as before.
- Returning to r4 **after writing r5 data is not a supported data rollback**: r4 does not understand attachment AAD. Use r5 snapshot restore, or restore a separately retained pre-upgrade backup into a compatible app. Keeping the database version unchanged avoids an unnecessary database-open barrier; it does not imply cryptographic backward compatibility.
- Security maintenance temporarily needs space for new ciphertext and snapshot copies. A storage/quota/crypto failure aborts the transaction. Browser eviction/real device quota behavior was not simulated on a phone.
- Cancellation after a report reference transaction has already committed can leave an unused reference number; it still prevents a subsequent download. Already completed downloads cannot be revoked.
